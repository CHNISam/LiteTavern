# 原型优先与角色素材来源约束

## 问题

在未先逐页核对产品原型、也未确认首发角色和素材来源时，直接制作了通用聊天界面并自行补角色与素材。结果偏离 `docs/v0.1.0/product/页面/` 的设计基准，也产生了应当丢弃的无效工作。

## 根因

- 把“实现聊天产品”误当成可自由设计 UI，没有先建立原型逐页映射。
- 在角色未由用户拍板前推进角色内容。
- 忽略“角色卡导入是角色数据与素材入口”这一产品约束。
- 完成判断只关注功能可运行，缺少与原型截图对照的验收门。

## 已采用的约束

- 四张原创原型图是 v0.1.0 UI 的唯一实现基准；开始 UI 工作前先以原始分辨率检查。
- 首发角色由用户确认；当前只确定为流萤，不内置未经确认的角色卡或官方素材。
- 角色名称、头像、设定和开场白以导入的 SillyTavern Character Card V2/V3 为数据源。
- 功能实现与视觉精修分开交接；当前代码只提供可运行、可测试的页面闭环。
- UI 完成前必须逐页截图对照原型，记录未还原项，不以“风格相近”代替验收。

## 防复发检查

1. 原型文件是否已逐页列出并确认页面状态？
2. 角色及其素材来源是否已由用户确认？
3. 是否错误地新增了硬编码角色、占位人设或未经授权的素材？
4. 页面流程和业务数据源是否先于视觉细节打通？
5. 交接时是否明确区分功能完成项、视觉待办和待确认业务规则？

## 验证

- 默认角色列表为空，不再注入虚构角色。
- 角色由 JSON/PNG 卡导入，并保留原 PNG 作为头像与同格式导出源。
- 聊天、档案、记忆、设置四页均已有功能基线；视觉精修留给后续 UI Agent。
