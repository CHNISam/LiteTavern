# 现行资料与用户 Chrome 的来源优先级

## 问题

在 LiteTavern v0.1.0 收口审计中，错误地查看了 `docs/archived/**` 内的历史截图，并在机器已经安装 Chrome 的情况下尝试安装 Playwright 浏览器。前者可能把过期决策带回当前实现，后者会无谓改变用户开发环境、占用磁盘并拖慢验收。

## 根因

- 把“仓库内存在”误当成“当前可信来源”，没有先按目录语义区分现行文档与归档资料。
- 把自动化工具的默认浏览器安装提示误当成必需步骤，没有先确认可复用的本机 Chrome 控制通道。
- 验收准备阶段缺少“先盘点现有能力，再引入依赖”的硬门禁。

## 已采用的解决办法

- `docs/archived/**` 只用于明确要求的历史追溯，不参与当前产品、架构或视觉决策；当前实现依据来自现行源码、测试、非归档文档和用户最新指示。
- 浏览器 E2E 优先连接用户现有 Chrome；不得因为测试框架提示而自动下载 Chrome、Chromium 或其他浏览器。
- 只有现有环境确实无法满足验收，且替代方案已排除时，才说明安装内容、体积和影响并请求用户明确授权。
- 已停止 Playwright 浏览器安装路线，后续 v0.1.0 主路径验收使用现有 Chrome。

## 防复发检查

1. 资料是否位于 `archived`、`deprecated`、备份或迁移目录？如果是，默认排除。
2. 当前决策是否能由现行源码、测试、ADR、研究文档或用户最新指示确认？
3. 调用安装命令前，是否已经盘点系统已有软件和项目已有依赖？
4. 浏览器验收是否可以直接复用用户现有 Chrome？
5. 安装会否改变用户机器、占用大量磁盘或引入长期维护项？如果会，是否取得明确授权？

## 验证

- 后续审计与实现不再读取 `docs/archived/**`。
- 浏览器验收切换为 Chrome 插件控制通道，不再执行浏览器安装命令。
- 本约束记录在非归档、可检索的 `docs/solutions/integration-issues/` 中，供后续仓库任务复用。
